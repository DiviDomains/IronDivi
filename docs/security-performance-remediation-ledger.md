# Security and performance remediation ledger

This ledger records the disposition of every finding in the IronDivi security and performance review: the 23 numbered security findings, the Medium and Low security notes, the dependency and build items, the performance findings, and the six areas the review did not cover. It covers the commits from the review baseline `3dfacf7b` to `bee99208`, plus the final integration candidate described in [Release disposition](#release-disposition).

Both clients stay first-class. C++ `divid` is not being retired: the consensus rows compare irondivid against it, and every consensus activation still held in [Active holds](#active-holds-and-lift-criteria) is to happen in both clients in lockstep.

Each row has one status:

- **accepted**: the change is in the tree and the evidence cited for it passed. It is not a certification. A measured performance win is a local benchmark, not a production latency guarantee.
- **disproved/excluded with evidence**: the finding, or a proposed change, does not hold or was measured and rejected, for the reason given.
- **held/disabled**: the affected capability is switched off or refused until a lift criterion is met.
- **open**: not fixed, or only partly fixed; the residual column says what remains.

A row is never moved to accepted because of a hold, a document or an argument alone. Source references are at `bee99208` unless a row names this candidate. C++ references are to Divi Core at `1b553a3b` (`divi/src/`).

## Difficulty retarget boundaries

`crates/divi-storage/src/chain.rs` `difficulty_boundaries_are_admitted_as_divi_core_computes_them` builds a 107-entry testnet block index and, for parents at heights 0, 1, 23, 24, 25, 53, 83, 99, 100, 101, 102, 103, 104 and 105, compares `Chain::get_next_bits` with a 128-bit transcription of Divi Core's `DifficultyAdjuster` (DifficultyAdjuster.cpp): the PoW limit below 24 blocks, Dark Gravity Wave over 24 blocks with the timespan clamped to [T/3, 3T] in both directions, and the PoS rule `bnNew * (39*60 + 2*spacing) / (41*60)` after the last PoW block, including a negative spacing (taken as 1), a zero spacing, a result of zero (replaced by the PoS limit 0x1e00ffff) and a very long spacing. For every parent, the required bits pass the `check_block_work` step of `accept_block_ref` (the block then fails only on its proof, as expected for a synthetic block), and the required bits ± 1 and with the exponent changed are each refused with `bad-diffbits`, score 0, before any proof check. `check_block_work` is enabled for Divi mode only; PrivateDivi skips it (see the B1/B3 hold).

## SetCompact ports

Divi Core has one decoder, `uint256::SetCompact` (uint256.cpp:296-314), and one encoder, `GetCompact` (uint256.cpp:316-337). IronDivi has three decoders:

| Decoder | Used by | Canonical bits | Non-canonical bits |
|---|---|---|---|
| `Hash256::from_compact` (crates/divi-primitives/src/hash.rs) | PoW check in `accept_block_ref` (chain.rs), `difficulty.rs`, the PoS coin-age target (`pos_validation.rs`), staker, RPC and snapshot | Equal to Core | Masks 0x00ffffff, so a set sign bit is read as mantissa where Core reads 0x007fffff and flags negative; exponents 33–34 truncate exactly as Core does |
| `divi_consensus::target::Target::from_compact` | `pos_calculator.rs` | Equal to Core | Zero for a set sign bit or an exponent above 32 |
| `target_from_compact` (crates/divi-network/src/sync.rs) | Header pre-check of PoW-height headers in sync | Equal to Core | Zero for a set sign bit, a zero mantissa, exponent 0 or an exponent of 33 and above; the caller refuses zero (`InvalidBits`) |

`compact_target_decoders_match_set_compact_on_canonical_bits` (sync.rs tests) checks all three against a transcription of `SetCompact` on every `GetCompact` output for 32 exponents × 11 mantissas plus the PoW/PoS limits of every network and known historical bits (more than 250 encodings). `compact_target_decoders_on_non_canonical_bits` pins each decoder's behaviour on negative, zero-mantissa, exponent ≤ 3 and exponent > 32 inputs, and records Core's `pfNegative` / `pfOverflow` for each.

Disposition: **disproved/excluded with evidence** in Divi mode, no code change. A connected Divi-mode block must carry exactly `get_next_bits(parent)` (`check_block_work`, before any target decoding), and `get_next_bits` always produces a canonical `GetCompact` encoding, so non-canonical bits never reach a decoder on the consensus path; the sync pre-check refuses them earlier, as Core's `CheckProofOfWork` does (negative or zero target). Residual risk: PrivateDivi mode skips `check_block_work`, so there a non-canonical negative encoding would be decoded differently by `Hash256::from_compact` than by Core. That is reachable only on PrivateDivi chains and is covered by the PrivateDivi mainnet hold (B1/B3).
